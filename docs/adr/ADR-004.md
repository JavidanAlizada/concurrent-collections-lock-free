# ADR-004 — Bounded vs Unbounded Queues

## Context

`MpscQueue` needs a capacity policy. Producers can outrun a single consumer
indefinitely under the wrong workload, so the queue has to decide what
happens when that gap grows.

## Constraints

Milestone 2's brief calls out capacity as an investigate item. Whatever is
chosen has to compose with the non-blocking `offer()` contract already
decided for this milestone (matches `java.util.Queue.offer()`, not a
blocking `put()`).

## Options

- **A — Bounded, fixed capacity set at construction.** `offer()` returns
  `false` once the limit is reached; caller decides whether to retry, drop,
  or apply backpressure upstream.
- **B — Unbounded**, like `ConcurrentLinkedQueue` — `offer()` always
  succeeds, the list just keeps growing.
- **C — Bounded with a blocking `offer()`**, like `ArrayBlockingQueue.put()`.
  A different primitive (this milestone already committed to non-blocking
  `offer()`), not a variant of the same one.

## Decision

A — bounded, fixed capacity.

## Rationale

- A single, possibly slow consumer facing N producers is exactly the
  scenario where unbounded growth turns a slow consumer into unbounded
  memory growth — the queue itself becomes the leak.
- Bounded capacity gives producers an explicit backpressure signal
  (`offer()` returning `false`) instead of silently absorbing an ever-
  growing backlog. What a caller does with that signal (retry, drop,
  block elsewhere) is a policy decision this queue deliberately doesn't
  make for them.
- Real MPSC use cases this design is modeled after (event loops,
  disruptor-style ring buffers) are almost always bounded for this exact
  reason.

## Trade-offs

- Producers now have to handle `false` from `offer()` — more ceremony than
  an always-succeeds unbounded queue.
- A capacity set too low under real load turns into constant `offer()`
  failures; too high defeats the point of bounding it. This queue doesn't
  pick a default — capacity is a required constructor argument, pushing
  that judgment call to the caller, who knows their workload.

## Consequences

Future queue-shaped structures in this project default to bounded unless a
specific reason argues for unbounded — that reason gets its own ADR, not a
silent choice.

## Alternatives

Would reconsider for a milestone specifically about unbounded-growth
trade-offs (e.g. demonstrating the OOM failure mode under sustained
producer/consumer imbalance) — that's a deliberate teaching goal for a
different milestone, not a gap in this one.
