# ADR-005 — Lock-Free vs Lock-Based

## Context

A stack's `push`/`pop` mutate one shared reference (`head`). That mutation
can be made safe either by CAS-retry (lock-free) or by a `ReentrantLock` /
`synchronized` guarding a plain linked-list mutation (lock-based).

## Constraints

Milestone 1's brief explicitly calls for a lock-free structure — this ADR
exists to write down *why* that's the right call, not to relitigate it.
Correctness must hold under N producer / M consumer concurrent access (see
the Milestone 1 proposal's test plan).

## Options

- **A — Lock-free (CAS retry loop).** Already implemented.
- **B — Lock-based (`ReentrantLock` guarding head mutation).**
- **C — Striped/partitioned locking.** Doesn't apply here: every push/pop
  contends on the same `head` reference regardless of striping — this is
  true sharing, not a partitionable access pattern.

## Decision

A — lock-free, via CAS retry loop.

## Rationale

- **Progress guarantee.** Lock-free guarantees *some* thread's CAS succeeds
  on every contended round, so the system as a whole always makes progress
  — even if a specific thread is descheduled mid-operation. A lock-based
  version has no such guarantee: a thread that's preempted while holding
  the lock stalls every other thread until it's rescheduled.
- **No blocking on the contended path.** A failed CAS just means "read
  `head` again and retry" — it stays in user space. A blocked lock
  acquisition can involve OS-level thread suspension and wake-up, which is
  a qualitatively different (and typically more expensive) kind of wait —
  though this project has no JMH numbers to put a figure on that (see the
  Milestone 1 implementation plan's scope-change note: benchmarking was
  dropped for this project).
- **No deadlock, no priority inversion.** There's no lock to hold, so the
  classic lock-based failure modes don't apply to this structure.
- Matches the task brief's actual point: demonstrate lock-free structures.

## Trade-offs

Written qualitatively — no benchmark backs any of this, by explicit project
scope decision:

- Lock-free code is harder to get right. A lock-based critical section can
  be ordinary sequential logic; the CAS retry loop has to be safe to
  re-execute in full, and every read outside the CAS needs its own
  publication/ordering argument (see `docs/design/aba-problem.md` and
  `docs/algorithms/treiber-stack.md`'s linearization-point argument).
- Under very high contention, CAS-retry can in principle burn more CPU on
  repeated failed attempts than a lock-based version would burn blocking a
  subset of threads — this is a real, documented effect in the literature,
  but this project makes no claim about which wins for `TreiberStack`
  specifically, since that requires measurement this project isn't doing.
- Lock-free here means lock-free, not wait-free: an individual thread has
  no per-operation progress bound under adversarial scheduling. That's the
  scope Milestone 1 set out to hit, not a gap.

## Consequences

Structures in this project default to lock-free per the task brief. If a
future milestone picks a lock-based design for a specific structure instead
(e.g. because a lock-free version is impractical for that data structure),
that's a deviation and needs its own ADR justifying it, not a silent
choice.

## Alternatives

Would revisit if a future benchmarking effort (contrary to the current
"dropped entirely" decision for this project) showed lock-based
outperforming lock-free at realistic contention for a specific structure.
Not being investigated here.
