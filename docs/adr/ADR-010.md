# ADR-010 — VarHandle vs Atomic* Concurrency Primitives

Not in the original brief's ADR list (`01-concurrent-collections-lock-free.md`,
which stops at ADR-009) — added mid-Milestone-2 when this decision came up.
Amends ADR-002's stated consequence; see that ADR's own amendment note.

## Context

`MpscQueue` needs an atomic exchange on `producerTail` and an atomic
counter for `count`. ADR-002 already answered this question for
`TreiberStack` (`VarHandle`, project-wide by that ADR's own "Consequences"
section) — this ADR revisits it specifically for this milestone.

## Constraints

ADR-002's rationale for `VarHandle` (demonstrate the JMM access-mode
spectrum directly, per AGENTS.md §3) hasn't changed and isn't being
relitigated. This decision is about whether every milestone must use the
same primitive, not about whether `VarHandle` was the wrong call in
Milestone 1.

## Options

- **A — `VarHandle`, per ADR-002's existing convention.** Consistent with
  Milestone 1; no new decision needed.
- **B — `AtomicReference`/`AtomicInteger` for `MpscQueue` specifically,
  `TreiberStack` left as-is.** A deliberate divergence, not a reversal.
- **C — `Atomic*` project-wide, retroactively.** Rewrite `TreiberStack` too,
  so the whole project is consistent on one primitive.

## Decision

B — `AtomicReference`/`AtomicInteger` for `MpscQueue`; `TreiberStack`
unchanged.

## Rationale

- The reason is comparative, not "`Atomic*` is better": showing both a
  hand-rolled `VarHandle` structure and an `Atomic*`-based one in the same
  portfolio, with trade-offs documented side by side (this ADR, ADR-007,
  `docs/algorithms/mpsc-queue.md`), teaches more than picking one
  convention and applying it uniformly without ever having to justify it
  against an alternative.
- Option C was rejected: rewriting already-shipped, already-tested
  Milestone 1 code to match would be churn for its own sake, with no
  correctness or teaching benefit — `TreiberStack`'s `VarHandle` usage is
  already fully justified by ADR-002 on its own terms.
- Ergonomically, `AtomicReference<Node<T>>` keeps full generic type safety.
  `VarHandle.findVarHandle` is inherently raw-typed (type erasure at the
  API level), which is why `MpscQueue`'s `VarHandle`-based first draft
  needed `@SuppressWarnings("unchecked")` casts on every access; the
  `AtomicReference` version needs none, since `AtomicReference<Node<T>>`
  is the real generic type end to end.

## Trade-offs

- **Loses manual cache-line padding as an option** (ADR-007,
  `docs/design/false-sharing-mpsc.md`) — `AtomicReference`'s internal
  value field isn't reachable from application code to pad around, unlike
  a `VarHandle`-targeted field this code declares directly.
- **Breaks project-wide uniformity.** A reader of this repo now has to
  know which milestone uses which primitive instead of one rule
  everywhere — a real cost to consistency, accepted here in exchange for
  the comparison being worth more than the uniformity.
- `AtomicReference`/`AtomicInteger` are themselves implemented via
  `VarHandle` internally in current JDKs, so this isn't "avoiding the
  atomic mechanism" — it's adding a wrapper object over the same
  mechanism ADR-002 already described. `Node.next` stays a plain
  `volatile` field in both versions either way: it's never the target of
  a compound atomic operation (no CAS, no exchange — one release-store,
  one acquire-load), so neither primitive would add anything over the
  language keyword there.

## Consequences

ADR-002's "Consequences" section states VarHandle project-wide; this ADR
is the documented exception for `MpscQueue`; ADR-002 has been updated with
a pointer here. The default for any future milestone is still `VarHandle`
per ADR-002 unless that milestone's own ADR states otherwise the way this
one did — this is not a blanket license to pick either primitive per
milestone without justification.

## Alternatives

Would reconsider Option C (retroactive uniformity) only if, in hindsight,
the comparison turned out not to carry its weight pedagogically. No
trigger condition is defined for that; not expected.
