# ADR-002 — Why VarHandle?

## Context

`TreiberStack` needs an atomic compare-and-set on its `head` field. Java
gives two realistic ways to do that: `java.util.concurrent.atomic.AtomicReference<T>`,
or a `java.lang.invoke.VarHandle` targeting the field directly.

## Constraints

This project exists to demonstrate lock-free algorithms and JMM reasoning
from first principles, not to wrap existing `java.util.concurrent`
abstractions (AGENTS.md §3). Several later milestones (queues, maps) will
also need CAS, so whatever's chosen here sets the pattern for the rest of
the project.

## Options

- **A — `AtomicReference<Node<T>> head`.** The obvious, idiomatic choice —
  most Java developers reach for this without thinking.
- **B — `VarHandle` on a plain `Node<T> head` field**, obtained via
  `MethodHandles.lookup().findVarHandle(...)`.
- **C — `sun.misc.Unsafe`.** Rejected outright: internal API, unsupported,
  and increasingly closed off by the module system.

## Decision

B — `VarHandle`. Already implemented in `TreiberStack`.

## Rationale

- `AtomicReference` only exposes volatile-strength get/set/CAS. `VarHandle`
  exposes the full JLS 17.4 access-mode spectrum — plain, opaque, acquire,
  release, volatile, `compareAndSet`, `weakCompareAndSet` — which is the
  actual thing this project is trying to demonstrate understanding of.
- `AtomicReference` is, in current JDKs, itself built on top of `VarHandle`.
  Using `VarHandle` directly removes a layer of indirection instead of
  hiding it.
- `AtomicReference<Node<T>>` needs a separate wrapper instance holding the
  reference; a `VarHandle` targets the `head` field in place — no extra
  object, no extra indirection to follow when reading the field.

## Trade-offs

No JMH benchmarking is being done for this project (see the Milestone 1
implementation plan's scope-change note) — so none of the below is a
measured performance claim, only a structural one:

- `VarHandle` setup costs more ceremony: a static initializer with
  `MethodHandles.lookup().findVarHandle(...)` and a checked
  `ReflectiveOperationException` at class-init time, versus
  `AtomicReference`'s one-line constructor.
- `VarHandle` is a less familiar API surface than `AtomicReference` — a
  reviewer who only knows `java.util.concurrent` will need to look up what
  each access mode means.
- The claim that `VarHandle` avoids an allocation is true by construction
  (no wrapper object exists), not something benchmarked here.

## Consequences

Every hand-rolled CAS field in this project (future milestones included)
uses `VarHandle` directly rather than `Atomic*` wrapper types, so the
project stays internally consistent about what it's demonstrating.

**Amended by ADR-010:** Milestone 2 (`MpscQueue`) deliberately diverges
from this and uses `AtomicReference`/`AtomicInteger` instead, as an
explicit, documented comparison — not a silent reversal. This ADR's
decision for `TreiberStack` is unchanged; see ADR-010 for the rationale
and trade-offs of the divergence.

## Alternatives

Reconsider if a future structure needs CAS over an array of references —
`VarHandle.arrayElementVarHandle` covers that case the same way, so this
isn't expected to force a reversal. Would only revisit if the
static-initializer boilerplate became a real maintenance burden across many
structures, which one data point (this stack) doesn't show.
