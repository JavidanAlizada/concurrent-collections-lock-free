# ADR-006 — Queue Node Representation

## Context

`MpscQueue` is a singly linked list. The one non-obvious design choice is
whether `producerTail` ever legitimately points at "nothing" (an empty
queue), and how that case is represented.

## Options

- **A — Stub/sentinel node**, allocated once at construction, that both
  `producerTail` and `consumerHead` reference initially. `producerTail`
  always points at a real node, never `null`. Vyukov's original design.
- **B — Nullable `producerTail`**, with an explicit `compareAndSet(null,
  node)` branch for the first insert into an empty queue, and ordinary
  linking after that.
- **C — No stub, no null-handling trick** — treat `count == 0` as the sole
  empty signal, with no dedicated first-insert case. Doesn't actually work
  standalone: it still needs *some* mechanism to resolve the
  producer-publish race window described in `docs/algorithms/mpsc-queue.md`
  §"The race window", and the stub node is what that mechanism reuses.

## Decision

A — stub node, matching the original algorithm.

## Rationale

- Removes a branch from every `offer()`: there's no "is this the first
  element" special case, because `producerTail` is never `null`. Every
  insert is the same unconditional exchange.
- The stub isn't just an empty-queue trick — `pushStub()` reuses the exact
  same node later to resolve the producer-mid-publish race window (see the
  algorithm doc). One piece of state does two jobs: represents "empty" at
  construction, and later helps the consumer distinguish "empty" from
  "producer hasn't finished publishing yet."

## Trade-offs

- A reader unfamiliar with the algorithm sees a "dummy" node with a `null`
  value and no obvious purpose until they read why it exists — it's not
  self-explanatory the way a plain `null` check would be.
- Reusing one long-lived stub instead of allocating a fresh one per
  recovery means its `next` field carries state across reuses. Getting that
  wrong (not resetting `stub.next` before re-publishing it) was a real bug
  caught during implementation — see `docs/algorithms/mpsc-queue.md`'s
  "Reusing the stub node correctly" section. The design isn't free of
  sharp edges; it just trades a null-check branch for a different
  invariant to maintain correctly.

## Consequences

Any future intrusive linked-queue design in this project (e.g. a
Michael-Scott MPMC queue in a later milestone) should consider whether a
sentinel node simplifies its own empty/first-insert handling the same way,
rather than defaulting to nullable head/tail pointers.

## Alternatives

Would reconsider if profiling showed the extra indirection through the
stub node mattered on the hot path — not measured here, this project runs
no JMH benchmarks.
