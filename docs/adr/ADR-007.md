# ADR-007 — False Sharing Mitigation

## Context

`producerTail` (written by every producer) and `consumerHead` (written only
by the consumer) are natural candidates for false sharing if they land on
the same CPU cache line — see `docs/design/false-sharing-mpsc.md` for the
full mechanism. This ADR is the decision record; that doc is the reasoning.

## Options

- **A — Manual cache-line padding.** Surround each hot field with enough
  unused bytes that it can't share a line with anything else. Only works
  when the field holding the actual contended value is one this code
  declares directly.
- **B — `jdk.internal.vm.annotation.Contended`.** Restricted to the JDK's
  own code; requires `-XX:-RestrictContended` to use from application
  code, which isn't a flag a library should require its consumers to set.
- **C — Accept it, don't mitigate.**

## Decision

C — not mitigated, for this milestone.

## Rationale

Option A requires the field taking the concurrent writes to be one this
class owns the layout of. `producerTail` is `AtomicReference<Node<T>>`
(ADR-010): the field on `MpscQueue` is a pointer to a separate JDK object,
and the field that actually receives `getAndSet` traffic lives inside
that object, at an offset this code doesn't control. Padding
`MpscQueue.producerTail` would isolate a pointer that's written once at
construction — not the thing under contention. Option B isn't available
to application code at all. That leaves C.

## Trade-offs

If `producerTail` and `consumerHead` do end up on the same cache line,
producer writes could invalidate the consumer's cached copy and vice
versa, adding contention neither role's own logic requires. Unmeasured —
this project runs no JMH benchmarks — so this is a structural risk being
named, not a quantified cost.

## Consequences

This is a direct, accepted consequence of ADR-010's choice to use
`AtomicReference` instead of `VarHandle` for this milestone, not an
oversight. A future `VarHandle`-based structure in this project with the
same asymmetric producer/consumer field split should apply Option A,
since `VarHandle` doesn't have this limitation — `TreiberStack` doesn't
need it today only because its single-CAS-point design has no such split
to isolate in the first place.

## Alternatives

Rewriting `MpscQueue` onto `VarHandle` would unlock Option A. Not planned:
doing so would erase the comparison ADR-010 exists to make.
